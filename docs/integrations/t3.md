# T3 Code backend (WIN-563 spike, WIN-564 session picker)

Talky `t3` profile → each turn goes to a [T3 Code](https://github.com/pingdotgg/t3code) thread, reply streams back.
Verified against T3 Code v0.1.0 on 2026-10-18.

## Setup

```bash
# No login step: Talky connects on first use (issues a narrow session, orchestration:read + :operate, 8h,
# → ~/.talky/credentials/t3.json, mode 600). `TALKY_T3_AUTOCONNECT=0` turns that off.
talky t3 login            # optional: issue the session by hand
talky t3 threads          # list T3 threads: running first, then newest
talky t3 attach <id|title>   # talk to that thread (opens the app unless --no-open)
talky t3 logout           # revoke the session, delete the file
```

Auto-connect: `/api/*` has no auth and the remote listener can expose it, so anyone who can reach the daemon can make Talky issue a T3 session. Set `TALKY_T3_AUTOCONNECT=0` to require an explicit `talky t3 login`.

Token lookup: `$T3_TOKEN`, else `$T3_TOKEN_FILE`, else `~/.talky/credentials/t3.json`. The daemon re-issues the session
(and revokes the old one) when under 15 min remain, using the `t3` CLI (`$T3_BIN`, `~/.t3/bin/t3`, or `PATH`). Tokens are never logged or printed.
Default runtime mode for threads Talky launches is `approval-required` (T3 shows "Supervised").

In the web app: sidebar → **T3 Code threads** (collapsed by default; on mobile it is at the bottom of the sessions drawer) → tap a thread.
That makes a Talky session bound to the thread (`backend: t3`, native session id = the thread id), seeded with the thread's last 12 messages;
the next typed or spoken turn is sent to that thread, history intact.

Config lives in `llm-backends.yaml` (`t3:`): `base_url`, `project_id` (default: T3's "No project" scratch project),
`instance_id` / `model`, `runtime_mode` (default `approval-required`). `$T3_BASE_URL` overrides the URL for the list/attach calls.

## How it works

- Transport: T3's app RPC (HTTP `/api/orchestration/shell`, WebSocket Effect-RPC with header/param protocol `2`), not MCP —
  `/mcp` rejects normal sessions (separate OAuth audience) and T3 exposes no ACP server.
- Turn 1 → `orchestration.launchThread` (new thread, `root` workspace). Later turns, or an attached thread →
  `orchestration.dispatchCommand` `message.dispatch`. Reply = polling `orchestration.getThreadProjection` (0.5 s) and emitting text growth as `TextFrame`s.
- Barge-in → `run.interrupt` on the active run (`thread.stop` is refused for clients).
- Thread watcher (WIN-605): while a thread is bound, Talky holds `orchestration.subscribeThread` open (the stream T3's own app uses)
  and speaks, in full, every run it did not start: timer and background-task wakeups, messages typed in T3's app or another client.
  Each push triggers one projection re-read; turns and the watcher share the "already sent" state, so nothing is spoken twice.
  History is not spoken on attach; a run already underway is spoken from that point on. Barge-in on a watcher reply only stops
  the speech (T3's run is not Talky's to interrupt). A turn longer than `run_timeout` is no longer cut off: the watcher finishes it.
- Sessions: the T3 thread id is the convo's native session id (`_session_id`), so resuming a Talky convo re-attaches to the same T3 thread;
  setting `thread_id` attaches to a thread that already exists.

- Turns are serialized: a turn spoken or typed while one is running is queued and runs after the current reply; a barge-in
  (user speaks over the reply) cancels the reply, interrupts the T3 run and drops the queue.
- Working cue: T3's first reply takes several seconds. After 2 s of silence the UI shows "⏳ T3 is working…" and a soft double tick plays (repeats every 6 s).
- Gotcha for fake-mic rigs: Chrome's `--use-file-for-fake-audio-capture` fails silently on a path containing `..`; pass a resolved path.
  A looping wav that repeats the question every few seconds barges in on itself (T3 shows "Run interrupted"); use long trailing silence.

## Not done

Approvals (T3 `runtimeRequests` aren't surfaced as Talky permission asks), turn replies still poll (the watcher uses `subscribeThread`),
model/effort picker, project picker UI. Code: `t3.py` (service), `t3_client.py` (RPC), `t3_threads.py` (list/attach), `t3_auth.py` (token).

## "Permissions have changed for MacBook Pro" in T3

Not caused by Talky's bearer sessions. T3's web/desktop client shows that toast (`PermissionUpdateNotice.tsx`) when *its own* browser session
was paired with a reduced scope set (`sessionHasLegacyPermissions`). Pairing a browser with `t3 auth pairing create --scope orchestration:read`
reproduces it (WIN-564). Re-pair with the default scopes, or Dismiss.
